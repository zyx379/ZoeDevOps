## 一、功能概述

运维人员在发布前需要了解：从当前线上版本到预发布版本之间，**改了哪些代码、涉及哪些需求、谁改的、是否通过审核**。

### 核心输入形式

用户提供多行文本，每行一个服务及其预发布版本：

```
收费前端 release-1.168.14
医嘱后端 release-1.168.25
门诊前端 release-1.168.13
医嘱前端 release-1.168.22
药剂前端 release-1.168.17
收费后端 release-1.168.41
```

系统自动查询每个服务的线上版本，进行版本比对，汇总展示。

### 版本比对策略

每个服务对应一个 GitLab 代码仓库（或多个）。系统根据服务名称匹配仓库，根据版本号确定 Git ref（分支/tag），然后获取两个版本之间的 commit 列表。

关键设计点：
- 同一服务名可能对应多个仓库（如"医嘱前端"涉及前端仓库和公共依赖仓库），全部纳入比对
- 版本号格式统一为 `release-X.Y.Z`，通过规则解析出对应的 Git 分支
- 比对结果按需求（commit）汇总，相同项目的 commit 合并显示

## 三、输出格式

### 表格列定义

| 列名 | 说明 |
|------|------|
| 提交人 | commit 作者 |
| 需求标题 | commit message 第一行 |
| 模块 | 涉及的代码仓库名称，多仓库用逗号拼接 |
| 最后提交时间 | commit 创建时间 |
| 状态 | 已通过 / 未通过 / 审核中 / 未标注 |

### 状态来源

从 commit message 中约定的标记提取，如 `[PASSED]`、`[FAILED]`、`[REVIEWING]`。无标记默认"未标注"。

---

## 四、交互流程

1. 用户在文本框中粘贴/输入服务+版本列表
2. 点击"开始比对"
3. 系统逐行解析，获取每个服务的线上版本和对应仓库
4. 调用 GitLab 获取 commit 差异
5. 结果合并去重后，以表格形式展示
6. 支持按提交人、模块、状态筛选
7. 支持导出 Excel

## 五、实现记录

### 已落地内容

1. 新增顶部导航入口"需求管理"，页面文件为 `renderer/pages/Requirements.tsx`。
2. 新增主进程比对服务 `main/requirements/versionCompare.ts`，负责：
   - 解析多行输入，格式为 `服务名 release-X.Y.Z`
   - 通过项目配置中的 API Base URL / Version Path 查询线上版本（Token 从 Redis 自动获取，请求头 onelinkToken）
   - 根据项目代码仓库配置的名称和匹配模式，支持一个服务匹配多个仓库
   - 将线上/预发布版本解析为 Git 提交 SHA 后 compare，仅返回预发布相对线上新增的 commits（非分支级全量差异）
   - 按 commit 去重聚合，合并涉及模块和服务
   - 从 commit message 中提取 `[PASSED]`、`[FAILED]`、`[REVIEWING]` 状态
3. 新增 IPC：`requirements:compareVersions`，并通过 `window.electronAPI.requirements.compareVersions` 暴露给渲染进程。
4. 补齐已有的 `api:getModuleVersions` IPC，复用 `ApiClient.getModuleVersions()` 获取线上模块版本。
5. 前端结果支持：
   - 服务级比对明细展示
   - 按提交人、模块、状态筛选
   - Excel 导出
   - 点击跳转 GitLab commit 详情
   - 表格状态列支持下拉修改（本地会话内生效，导出 Excel 含修改后状态）

### 使用前配置

1. 在"项目管理 > API & Redis 配置"中配置 API Base URL、Version Path 和 Redis，用于读取线上版本（Token 从 Redis 自动获取，逻辑与智能分析一致）。
2. 在"项目管理 > 代码仓库配置"中维护服务名匹配模式和仓库地址。
3. 在"全局配置 > GitLab"或仓库级配置中配置 GitLab Token。
